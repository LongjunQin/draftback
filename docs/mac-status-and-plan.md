# 电脑版:现状、架构与剩下的工作(2026-10-14)

> 给产品负责人看。回答三个问题:电脑版功能做到哪了、软件架构要不要改、接下来按什么顺序做。数据按今天的代码核实(分支 rename/draftback,提交 59516d8)。

## 0. 先说结论

| 你的问题 | 回答 |
|---|---|
| 电脑版功能做到哪了 | **闭环的主干已经通了,常用的阅读器功能也补齐了。** 普通阅读、普通编辑、审阅三种状态分开;划词批注精确到字;原文冻结;智能体按批注改稿后自动刷新;编辑保存只改你动过的块;推到手机、收批注、回执、改稿摘要都能用。剩下的是「让闭环好用」的那层(稿子在谁手里一眼看清、改了什么一眼看清、能退回改稿前)和十来件常规小功能。 |
| 架构要不要改 | **不用推倒,要做三处整理。** 四块分工(Electron 外壳、本地服务、网页界面、同步辅助程序)是对的,Mac 不换原生壳(路线图 6.1 的判定条件已满足:Electron 接 CloudKit 顺利)。要整理的是:界面代码一个文件 2700 行要拆开;菜单和动作要合成一张表;每轮改稿前的原文要存一份。都是「整理」,不是「重做」。 |
| 是不是电脑、手机、打通三件事,功能做完最后改 UI | **是四件事,顺序要调一下。** 第四件是「分发」(签名公证、云端生产环境、TestFlight 或商店),你已定等定版后做。顺序上,UI 分「骨架」和「皮肤」:骨架(菜单怎么排、工具栏放哪六样、状态区在哪)决定每个功能住在哪,**要在做功能之前定**,否则功能做完还要搬一次家;皮肤(颜色、字体、间距、图标)放最后统一调。所以建议:先过 UI 方案的 13 问定骨架(这就是产品定义),再做电脑版功能,再做手机版,打通的可靠性验收穿插其中,最后皮肤和分发。 |

## 1. 电脑版现在能做什么

按你用的时候的视角列,每一项都有自动化测试或装机验证。

| 场景 | 现在能做的 |
|---|---|
| 打开与阅读 | 双击 .md、⌘O、从访达拖进窗口、智能体 `mdreview open` 直接送到面前;多标签;左栏大纲;正文缩放;深色模式跟随系统;⌘F 查找(计数、上下个、高亮);公式、Mermaid 图、代码高亮、表格、任务列表;最近文件(左栏与欢迎页);GBK / UTF-16 编码的文件按原样显示、只读不写坏 |
| 普通编辑 | 所见即所得编辑;⌘S 保存只改你动过的块,其余字节不变(含 Front Matter、原始 HTML、公式、列表缩进);覆盖前自动备份(每篇留 10 份);文件在外面被改会重新载入;编辑期间智能体不能冻结这篇(编辑登记) |
| 审阅闭环 | 「开始审阅」冻结原文并记指纹;划词批注,标题、表格、代码块、跨段落都能选;「完成本轮审阅」;智能体 `begin-apply` → 改文件 → 逐条标「已处理 / 不处理」→ `complete --summary`;回稿自动刷新;冲突、取消、定稿、人工解锁后自己改,语义齐全;每条批注的去向有记录,一轮轮往下走 |
| 手机联动 | 开审阅时自动推到手机(正文、图片附件、状态);手机批注交回后 Mac 自动收下并回执;改稿中手机看到横幅;改完手机正文自动换新并带摘要;`mdreview sync-status` 看每篇状态 |
| 导出 | PDF(⇧⌘E)、打印(⌘P)、单文件 HTML、Word(需电脑装有 pandoc) |
| 新建 | ⌘N 或欢迎页新建,选位置后直接进编辑 |
| 安全与数据 | 文档里夹带的原始 HTML 不执行、Mermaid 严格模式、内容安全策略;本地服务只听本机并校验来源;整体快照备份与恢复(`mdreview snapshot / restore`);审阅索引启动自清理;保存中断自动恢复 |
| 给智能体的命令 | `mdreview` 共 12 条:open、status、wait、begin-apply、complete、push、sync-status、unlock、snapshot、snapshots、restore、import-batch |

**还没有的**(来自 UI 方案 1.2 节的「要补」与第 6 节):设置窗口、菜单栏里的「打开最近文件」子菜单、「在访达中显示」、「另存为副本」、粘贴为纯文本、快速打开、编辑模式的查找替换、字数统计、图片粘贴落盘到文档旁、任务列表阅读时的只读勾选框、⌘K 插入链接;以及闭环体验层:状态区、「交给 AI」主按钮、回稿卡、显示改动、恢复到第 N 轮改稿前、「我自己改」。

┌──────────────┐   HTTP(本机)  ┌──────────────────┐    文件    ┌──────────────┐
│ 回稿 App     │ ───────────▶ │ 本地服务          │ ────────▶ │ 你的 .md     │
│ Electron 外壳│              │ (随 App 启动)      │          │ + 旁注文件    │
│ + 网页界面   │ ◀─────────── │ 审阅状态机、保存、 │          │ .annotations │
└──────────────┘   事件推送    │ 同步队列、快照     │          └──────────────┘
                              └─────────┬────────┘

                              ┌─────────▼────────┐    iCloud    ┌──────────┐
                              │ 同步辅助程序      │ ◀──────────▶ │ iPhone   │

                              └──────────────────┘              └──────────┘

## 3. 架构要不要改:三处整理,其余不动

**不动的**:四块分工;继续用 Electron(不做原生壳);本地服务 + 文档旁注文件的协议;所见即所得编辑 + 块级回写;`mdreview` 命令与旁注文件格式(智能体和旧数据都靠它)。

**要整理的三处**(每处一到两天,都不改用户看到的行为):

| 整理 | 做什么 | 为什么 | 什么时候 |
|---|---|---|---|
| ① 界面代码拆模块 | desktop.js 按「标签与文档 / 阅读与批注 / 编辑 / 查找与导出 / 状态与同步」拆成五六个文件 | 接下来要加十几个功能,一个 2700 行的文件会成为每次改动的风险源 | 做第二批功能之前 |
| ② 菜单与动作合一 | 把「动作名、快捷键、在菜单哪、在工具栏哪、什么状态下可用」做成一张表,菜单栏和工具栏都按表生成 | UI 方案 1.3 节的菜单栏要整体重排,现在菜单在外壳里、动作在界面里,两处对着改容易漏;有了表,改快捷键只改一行 | 落 UI 骨架时 |
| ③ 每轮改稿前存原文 | 服务端在「交给 AI」时存一份冻结原文(留 10 轮) | 「显示改动」「恢复到第 N 轮改稿前」「回稿卡」都要它;现在只有指纹没有全文 | 第一批功能的第一项 |

**知道但不急的技术债**:快照整份复制(每份约 1.3 MB);导出 Word 依赖 pandoc(公开版前定随包还是换纯 JS);Windows 包自 0.4.1 后没重打;编辑模式没有查找替换。

## 4. 电脑版剩下的工作:三批

| 批 | 内容 | 验收 |

## 5. 总流程建议(电脑、手机、打通、分发怎么排)

你设想的是「电脑 → 手机 → 打通 → 功能都完了最后 UI」。我建议改成下面这样,差别在两点:**骨架提前、皮肤最后**;**打通已经通了,剩的是可靠性验收,穿插做**。

| 阶段 | 做什么 | 为什么这么排 |
|---|---|---|
| A 定义(先做,一次过) | 过 UI 方案第 6 节的 13 问 + 第 1 节功能边界 | 这就是「产品定义」。闭环动作两端要一致(交给 AI、回稿卡、显示改动、定稿),所以电脑手机一起定,不分开定 |
| B 电脑版 | 第 4 节三批,顺序:第一批 → 第二批 → 第三批 | 第一批是差异点,先做;第二批是补齐;第三批骨架落地后皮肤只是调参 |
| C 手机版 | UI 方案第 4 节:底栏「批注这段 / 交给 AI」、回稿卡、逐条结果、手机定稿、稿子回来直接开下一轮 | 其中三件要改服务端(手机定稿、直接开下一轮、逐条结果推到手机),在 B 阶段做服务端时顺手改好,C 阶段只做手机界面 |
| D 打通的可靠性 | 跨端规则第 11 节五个场景:断网、强退、重复提交、旧版本返回、回传中断;再加今天这种「云端环境被重置」 | 通道已通,缺的是故障下不丢意见、不改错稿的验收。穿插在 B、C 之间做,每次出包顺手验一两个 |
| E 皮肤统一 | 两端一起调颜色、字体、间距、图标 | 放最后是对的,但只放「皮肤」 |
| F 分发 | 商标与域名(你办)、CloudKit 生产环境、Developer ID 签名公证、TestFlight、商店 | 你已定等定版后 |
