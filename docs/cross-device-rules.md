# 回稿 跨端规则(v2.4,2026-10-15)

> 路线图 v3 第 5 节的落地文档。它回答一个问题:同一份文档在 Mac 和 iPhone 之间来回时,**谁说了算、怎么认出是同一份、批注怎么走、出了岔子怎么办**。代码按这份规则写,验收也按它验。不懂技术也能读:每条规则先说人话,再给实现要点。
>
> **v2.3 改动(2026-10-14)**:按已拍板的[轮次版本记录设计 v4](version-record-design.md)与[电脑版规划 v3](mac-status-and-plan.md)修订合同层(经 Codex 只读审查,无需新增产品决定)。核心是把"同一正文"与"同一轮身份"彻底分开:文档标识跨轮稳定、每轮独立身份、恢复产生新身份;批次协议升到 `version: 2` 并逐条带身份;正文按版本事件从归档发布,不拿工作稿冒充;云端发布带 `revision` 防回退;手机正文缓存绑定自己的身份;监听与领取分开。第 13 节标明每条规则的实现阶段——合同在电脑端阶段定下,手机界面按"电脑端做完再做手机"的顺序,只有协议兼容的小改动与功能同批上线。
>
> **v2.4 改动(2026-10-15,手机第三步)**:按电脑版规划 v3 已定的"手机也能开下一轮、能定稿、能看逐条结果"补合同,设计经 Codex 审查后重写。① 带意图的批次是 `version: 3`(`next-round`:稿子回来后在手机上批注,交出时 Mac 开下一轮、收批注、交出;`finalize`:手机定稿),旧 Mac 一律拒收;Mac 在快照里写 `macProtocol`,手机按它决定给不给这两个功能;② 开轮与定稿都是带导入日志、锁内判断、可重放的事务,接受回执是提交点;③ 批注创建身份不改,"为下一轮写的"在创建时就标 `intent`,收下后另记 `acceptedReviewId`;④ 终态快照带本轮处理结果(已实现);⑤ 手机应用回执可恢复;⑥ "复制到本轮"(第 6.8 条)落地。

> v2.2(2026-10-14)只把容器与内部标识换成新名;v2(2026-10-13)定了四个产品决定:只推进入审阅流程的文档;`mdreview open` 即自动推、`complete` 即自动推新版;默认 Mac 常开;改完一轮手机收到新版正文加一段改稿摘要。命名沿革见 [naming-history.md](naming-history.md)。

## 1. 几个词

| 词 | 意思 |
|---|---|
| 文档 | 一个 `.md` 文件。Mac 上它有路径;到了手机上,它只是一份内容。 |
| 文档标识(`docId`) | 文档的身份,**跨轮稳定**;由 Mac 的文档身份索引(`documents.json`)管理,不写进文档本身。 |
| 会话标识(`reviewId`) | **一轮**审阅的身份;每轮一个,恢复也产生新的一个。 |
| 轮次 | 文档的第 N 轮审阅,轮号由文档身份索引**单调分配**,不因历史清理回退。 |
| 版本指纹 | 文档内容算出的 SHA-256。它标识实际字节,**不能代替**文档或轮次身份。 |
| 版本事件 | 每轮留底的记录:原稿、完成稿、处理结果、摘要;类型有 AI 改 / 我自己改(`review`)、零批注通过(`approved`)、作废(`cancelled`)、独立手工修改(`manual`)、恢复(`restored`)。 |
| 本轮成员 | 交出那一刻固定的本轮批注集合;之后新加的进下一轮。 |
| 批注批次 | 手机上点「交给 AI」时打包的一组批注,协议 `version: 2`。 |
| 快照包 | 推到手机的那一份:正文、图片附件、版本指纹、会话与事件信息。 |
| 回执 | Mac 收到批注批次后发回手机的确认:收了几条、拒了几条、为什么。 |
| `revision` | 同一文档下跨轮单调递增的发布序号,云端与手机据此拒绝旧发布。 |

## 2. 两种流程,分开管

### 2.1 Mac 发起的审阅(主线)

人话:智能体在 Mac 上写好文档、用回稿发起审阅,手机上就自动出现这份文档;你批完点「交给 AI」,批注回到 Mac,智能体接着改;改完新版又自动回到手机。

规则:

- **按事件发布。** `mdreview open` 建轮即自动上云、推到手机;轮次进入终态(完成、零批注通过、作废、恢复)再发布一次。普通打开(没有进入审阅流程)的文档一个字节都不上云。
- **正文从归档读。** 冻结时发布冻结原稿;终态正文按第 5 节的表从不可变归档读取,**不拿后续实时工作稿冒充该轮归档稿**;终态之后用户在 Mac 普通编辑产生的是工作稿,不推。
- **原文归 Mac。** 原文件只在 Mac 上,手机永远不改原文,只提交批注。
- **轮次归 Mac。** 开新一轮、交出、完成、定稿、作废、恢复,都由 Mac 的会话状态机与文档身份索引决定。手机可以按合同**请求**开轮、交出、定稿,以 Mac 校验成功并发布的结果为准(手机界面后续阶段实现,记录格式现在定)。
- **手机针对指定轮次与版本提交。** 批次与每条批注都带 `{docId, reviewId, baseVersion}`;Mac 收到时核对,不一致就拒收并说明。

### 2.2 手机独立打开的文件(副线)

人话:你在手机"文件"里打开任意一份 Markdown,读、批、改、导出。

规则:

- 它和 Mac 的会话**无关**,即使文件名一模一样;有自己的本地记录,不会自动与 Mac 的会话合并。
- 不提供自动回传 Mac。它导出的批次没有 Mac 轮次身份,只能在 Mac 上用 `mdreview import-batch <文件> --as-new-notes` **显式转换为当前轮的新批注**(新 ID、保留来源),不会冒充任何一轮。

## 3. 怎么认出是同一份

人话:不靠文件名,不靠 Mac 上的路径。文件改名、挪位置,要在回稿里确认一次,会话和历史就跟着走;复制一份、另存为,算新文档;恢复旧稿是新的一轮、新的身份。

规则:

| 标识 | 是什么 | 谁发 | 存在哪 |
|---|---|---|---|
| 文档标识 `docId` | 文档身份,跨轮稳定 | Mac | 文档身份索引 `documents.json`(含当前路径、下一轮轮号、最新版本);**不写进文档本身** |
| 会话标识 `reviewId` | 一轮的身份 | Mac | 审阅索引 `reviews.json` |
| 版本事件 `versionId` | 一轮留底的目录名 | Mac | `versions/<docId>/<versionId>/` |
| 版本指纹 | SHA-256 | Mac 算,手机核对 | 快照包、批注批次、回执里都带 |

- **身份与指纹分开**:正文指纹只证明字节相同,不证明是同一轮;恢复旧稿后正文与旧轮完全相同,身份仍是新的。
- **在回稿里改名**(双击文件名,或菜单「文件 → 重新命名…」):同一文件夹里换名字,身份、各轮记录、旁注跟着走;这一轮没走完时不让改;改过名的文档名字进推送签名,重推一次,手机显示新名字。
- **改名、移动**:通过**受控重新关联**保留身份(`mdreview relink <旧> <新>`,或回稿里打开时发现同 `docId` 记录指向不存在的旧路径且内容指纹一致 → 提示确认)。不再仅凭正文相同自动沿用会话。重关联后旧路径的请求失效;目标路径已属于另一文档时拒绝。
- **复制、另存为**:新路径、新文档标识、新会话;相同正文不自动合并;旧会话不受影响。
- **恢复**:产生新的会话身份、轮号和版本事件,不复用被恢复轮次的身份。
- **手机侧**:只认文档标识 + 会话标识 + 版本指纹,从不接触 Mac 路径;展示用的文件名只是显示文字。
- **外部改动**:审阅期间 Mac 上的原文被别的程序改了,现有的冲突拦截照旧生效;冲突状态同步到手机,手机显示"原文已变,等待 Mac 处理",不再允许提交。

## 4. 谁说了算(状态权威)

人话:三方各管一摊。Mac 管原文、轮次身份、版本事件和最终状态;手机管自己还没交出去的批注;云端只是邮筒,不做裁判。

| 操作 | 谁发起 | 谁校验 | 谁最终落盘 |
|---|---|---|---|
| 推到手机 | Mac 上 `mdreview open` / 终态事件自动触发(也可手动 `mdreview push`) | Mac 会话状态机与版本记录 | Mac 写会话记录;云端存快照包 |
| 手机写批注 | 你在手机上 | 手机本地校验(正文字节通过本轮指纹才允许) | 手机本地(先落盘再说) |
| 交出(提交批次) | 你在手机上 | 手机打包;Mac 收到后按第 6 节顺序核对 | Mac 在同一事务里写入旁注、固定成员、推进状态、定稿回执 |
| 智能体改稿、完成本轮 | 智能体在 Mac 上 | 现有状态机 + 版本记录(先固化载荷再推进终态) | Mac;新版快照包从归档推到手机 |
| 定稿、作废、恢复 | 你在 Mac 上(或智能体 unlock);手机可请求定稿 / 开轮 | 现有状态机;恢复另按设计 v4 第 6 节 | Mac;状态同步到手机 |

- 手机本地保存、上传成功、Mac 接收、AI 领取是四个不同事件,界面不得互相替代。
- 桌面界面、CLI、同步模块遵守同一套状态转换规则,规则只有一份实现,三方都调用它。
- **云端可重建的范围**:Mac 可以重建它的权威正文、版本事件和回执;**手机尚未被 Mac 确认的批注与批次由手机自己保留**,不能宣称全部云数据都能从 Mac 重建。
- **兼容分两层**:旧数据可读取——老的旁注文件与审阅索引不做格式迁移就能用,文档身份索引允许回填;旧协议不可接收——没有身份的旧手机批次拒收并提示更新,旧文件批次只能显式转为新批注(第 2.2 节)。

## 5. 快照包里有什么

人话:推到手机的不只是文字,还有文档里引用的图片;推的正文是"这一轮"的正文,不是 Mac 上此刻的工作稿。

| 内容 | 规则 |
|---|---|
| 正文 | 冻结时发布冻结原稿;终态按下表从归档发布 |
| 版本指纹 | 所发布正文的 SHA-256 |
| 本地图片与附件 | 文档里相对路径引用的(含引用式图片)、位于文档目录树内的文件,全部打包;单个文件超过 20 MB 或总量超过 100 MB 时,超出的文件不打包,清单里标"未打包";缺失的标"缺失" |
| 资源清单 | 每个资源的相对路径、字节数、校验码、状态,保证手机看到的图是这一版对应的图;每个版本事件分别记冻结时与完成时的清单 |
| 外链图片 | 不打包、不缓存;手机联网时直接加载,离线时显示占位 |
| 指向其他 Markdown 的链接 | 首版在手机上显示为普通文字链接,不可跳转 |
| 会话与事件信息 | 文档标识、会话标识、轮次号、事件类型与结果、恢复来源、正文是否可用、编码、`revision`、监听 / 领取信息、推送时间、推送者 |
| 处理结果(v2.4) | 稿子回来(AI 改 / 我自己改)的终态带本轮逐条结果:本轮成员(Mac 上交出时固定的那些批注,含手机交来的)每条的引文、你说了什么、AI 怎么处理、状态,只传这几个字段;计数按全部成员。只从版本事件里固化的快照算(与 Mac 回稿卡同一个函数);**只跟着正文一起推**(正文没推就不推结果)。每个字段截到 600 字并标「…」,列表按 300 KB 字节预算放,放不下标 `truncated`。整条记录的非资产字段合计不超过 900 KB:摘要截到 20 KB,超出时先丢结果列表、只留计数 |

**终态正文来源**:

| 事件 | 发布正文 |
|---|---|
| `review`(AI 改 / 我自己改)、有实际写入的 `manual`、`restored` | 归档 `final` |
| `approved`(零批注通过) | 归档 `original` |
| `cancelled`(作废) | 只推状态 |
| 旧会话未归档、归档文件缺失或损坏 | 只推状态与摘要 |
| 归档文件完好、只是版本索引发布失败 | 照常推正文与结果(归档本身可用) |

- **编码**:非 UTF-8(GBK / UTF-16)文档在 Mac 保留原始字节,**首版不同步正文**,手机只收状态。
- **手机正文缓存绑定自己的身份**:缓存正文单独记录它实际对应的 `{docId, reviewId, baseVersion}`;仅状态更新**不得改挂**缓存身份;只有实际正文字节通过本轮指纹校验,才允许对本轮批注;新正文不可用时,旧稿按旧身份只读显示。
- **历史恢复只恢复 Markdown 正文**;附件按实际可得文件显示,并提示与历史清单的差异,不承诺恢复完整历史画面。
- 同一文档再次推送(新一轮)时,只传指纹变化的文件;手机按清单核对,缺什么补什么,复制后校验字节。

## 6. 批注怎么走:批次、回执、去重

人话:手机上写的每一条先存在手机里,强退也不丢;点「交给 AI」才打包上传;Mac 收到后回一张回执;重复上传不会重复算;旧轮的批注即使正文一模一样也进不了新轮。

规则:

1. **先落盘**。每条批注写入手机本地存储**成功**后才算"已保存"(写失败要明确反馈,不能当成已保存);创建时就固定它的身份 `{docId, reviewId, baseVersion}`。
2. **打包**。点「交给 AI」生成一个批次(`version: 2`):批次编号(随机)、外层身份 `{docId, reviewId, baseVersion}`、批注列表(每条带自己创建时的身份,打包**不得**用当前会话身份覆盖)、完成时间。内外身份必须一致。批次生成后,这一轮的批注在手机上锁定,不能再改;要改,等下一轮。协议版本由手机真实写出,经 CloudKit 与 Mac 辅助程序**原样传递**,桥层不得硬填版本或补造身份;批注列表缺失或不是数组的载荷整批拒绝,不能当成零批注。
3. **上传**。批次上传到云端(你自己 iCloud 账号的私有空间);失败自动重试;界面显示"等待同步"。
4. **Mac 接收,按这个顺序**:
   1. 批次编号见过且已有定稿回执 → **直接返回原回执**,不重复写入;有未完成的导入记录 → 先按记录收敛(第 5 条)。
   2. 缺任何一层身份 → 拒收 `missing-identity`,回执"请更新手机上的回稿"。
   3. 按 `docId` 定位文档;**有 `docId` 时禁止跨文档按指纹或文件名回退**,找不到就是 `no-session`。
   4. 对照**最新一轮的身份(含终态)**:批次的 `reviewId` 不是最新一轮 → 拒收 `round-advanced`("轮次已推进:这批对应第 N 轮,Mac 已是第 M 轮,请在手机上打开最新一轮再提交");指纹相同也拒。
   5. 会话还在批注中吗?不在(已交出、已进入改稿、已完成、已作废)→ 拒收 `session-advanced`。
   6. 版本指纹和 Mac **实际文件**一致吗?不一致 → 拒收 `version-mismatch`。
   7. 都通过 → 在**同一把文档锁、同一个可恢复事务**里:写入旁注(按批注 ID 去重,批次内与跨批次都去重)、固定本轮成员、会话进入"已交出"、定稿回执。写入前先持久化导入记录(目标身份、输入批次、算好的接受 / 跳过列表)。
   - **批次没有完整收到时不写入、不改状态**:宁可让手机重传,不能让智能体拿着半份批注改稿。
   - 完全不属于本机文档的云批次(别的 Mac 发起的审阅)由辅助程序忽略,不替别的 Mac 写拒收回执。
5. **崩溃重放**。同一批次再到达时按导入记录补齐未完成的阶段(旁注、成员、状态),最后定稿原回执;接受 / 跳过列表以记录为准不重算;**不凭"旁注里有没有这批批注"判断成功**。有未收敛的导入记录时,这篇文档不得进入改稿或开新轮。
6. **回执**。批次编号、接收时间、批次原身份与指纹、接受的批注 id、拒收原因。手机收到回执后把对应批注标为"Mac 已接收",或把拒收原因显示出来。
7. **迟到的旧批次**。按第 4 条拒收;手机上这些批注**保留**并标记"未被采用(原因)";不静默丢弃。
8. **重新发送、旧批注与本轮成员**。"重新发送"读取原批次快照,保持批次号、批注 ID 和创建身份;旧轮未交或被拒的批注保留原记录,用户显式"复制到本轮"才生成新 ID、本轮身份并保留来源;原记录不改挂。Mac 在交出时固定本轮成员(当时归属本轮且 open 的批注;缺 status 的旧记录按 open 兼容);处理提示、完成门槛、手机计数、回稿结果、归档都用同一成员集;交出后新增的批注留待下一轮,不阻塞本轮完成;交出前作废时固定当时成员;独立手工修改轮成员为空。

### 6.9 批次意图(v2.4,经 Codex 设计审查后重写)

人话:稿子回来后,你在手机上接着批,交出时 Mac 替你开下一轮;觉得可以了,在手机上点「定稿」。旧版本的 Mac 收到这类批次一律拒收,不会做错事。

**协议版本与能力声明**

- 带意图的批次是 `version: 3`,必须带 `intent`,取值只有 `next-round`、`finalize`;未知意图、`version: 2` 带意图、`version: 3` 不带意图,都按结构无效整批拒收。旧 Mac 不认 `version: 3`,同样整批拒收(回执 `invalid-batch`),手机提示"Mac 上的回稿需要更新"。
- Mac 在每次推送的快照里写 `macProtocol`(本版为 3)。手机只在最新快照的 `macProtocol ≥ 3` 时才提供"稿子回来后接着批"和"定稿";否则照旧提示"要接着改,在 Mac 上开下一轮"。
- 没有意图的 `version: 2` 批次按第 6.1–6.8 条处理,不受影响;`version: 1` 照旧拒收。

**批注的身份(不改第 6.1 条)**

- 为下一轮写的批注,创建时固定身份 `{docId, reviewId, baseVersion}` 指向**刚结束那一轮**与手机上那一版正文,另带 `intent: "next-round"`(创建时就定,之后不改)。没有这个标记的旧批注(上一轮没交的、被拒收的)不会被打进 `next-round` 批次,只能显式"复制到本轮"。
- Mac 收下后,回执给出 `targetReviewId`(新开的一轮)。手机**不改**批注的创建身份,另记 `acceptedReviewId = targetReviewId`;判断批注属于哪一轮时,`acceptedReviewId` 优先。

**"最新一轮"只有一个定义**:这篇文档最后建的那个会话(按创建先后),包括我自己改(独立手工修改)、恢复与进行中的轮;推送挑哪一条发、收批次判 `round-advanced`、定稿判"是不是最新",都用同一个函数。不再分别用"最大整数轮号"和"创建时间"。

**所有批次共用的入口规则**(v2、v3 都一样):定位到文档后,在**同一把文档锁里**依次:有定稿回执 → 原样返回(先收掉残留的导入日志);有未收敛的导入日志 → 先收敛;重读最新一轮;再按版本与意图判断接受或拒收。拒收回执也在锁里写,不会覆盖接受回执。

**在途导入的隔离**:这篇有未收敛的导入日志(或卡住的恢复)时,Mac 上写批注、开轮、交出、领取、开始改稿 / 我自己改、定稿、作废、进入编辑与普通保存,都先收敛它;收敛不了就拒绝并说明"手机交来的批注正在处理"。只有本事务自己(按批次编号)不受挡。

**`next-round`:Mac 开下一轮、收批注、交出,一个可恢复的事务**

- 批次外层与每条批注的身份一致,且每条都带 `intent: "next-round"`;至少一条批注。
- 全部判断在**同一把文档锁**里做,按顺序:已有定稿回执 → 原样返回(先收掉残留的导入日志);有未收敛的导入日志 → 先收敛;重读这篇的**最新一轮**,不是批次的 `reviewId` → `round-advanced`;最新一轮不是终态(完成、通过、恢复、定稿、作废之外)→ `session-advanced`;Mac 上有人在普通编辑这篇 → `user-editing`;原文件指纹 ≠ `baseVersion` → `version-mismatch`。拒收回执也在锁里写,不会覆盖已有的接受回执。两个 `next-round` 批次同时到,只有先拿到锁的能开轮,后到的 `round-advanced`。
- 都通过:导入日志先落 `stage: "reserved"`,预留新一轮的会话标识(轮号与留底目录在开轮时分配,开轮把预留的会话标识与 `openedByBatch` 一起首次写入);再在锁内开轮(冻结即留底)→ `opened` → 写入批注 → 固定成员并交出 → `submitted` → 写接受回执(**提交点**)→ 删日志。
- 重放:`reserved` 时按预留的会话标识找这一轮,找到就接着走,找不到才开(此时重新核对最新一轮、终态与指纹,不满足就写拒收回执并收掉日志);之后各阶段同第 6.5 条。留底目录已建、会话未写时,开轮按会话标识复用同一个留底,不留孤立的轮;重放决定拒收时,删掉这个事务建的、没有会话引用的留底目录(轮号不回收,跳号无害)。
- 隔离:这篇有未收敛的导入日志时,Mac 上写批注、开轮、交出、开始改稿都先收敛它(或拒绝,说明"手机交来的批注正在处理");`wait` 照常返回,但只有收敛完、写了回执之后才能开始改稿。

**`finalize`:手机定稿,一个可恢复的事务**

- 不带批注(`annotations: []`)。锁内先查:最新一轮不是批次的 `reviewId` → `round-advanced`;Mac 上有人在编辑这篇(编辑登记)→ `user-editing`;原文件指纹 ≠ `baseVersion` → `version-mismatch`(Mac 上改过,先在 Mac 上看);旁注里还有未处理的批注(交出后才写、等下一轮的那些)→ `has-open-notes`(先在 Mac 上处理或让它们进下一轮)。再按状态分派:稿子回来(完成)、零批注通过、已恢复 → 定稿;已定稿 → 原样接受,不改定稿时间;作废 → `session-advanced`;批注中 → Mac 上这篇**一条未处理的批注都没有**(整份旁注,不只是成员)才先零批注交出(记为通过)再定稿,否则 `has-open-notes`;已交出、改稿中、冲突 → `session-advanced`。
- 先通过再定稿也走导入日志:`approving` → `approved` → `finalized` → 回执 → 删日志;重放从断点接着走,不重复交出、不重写时间。
- 推送按版本事件的类型取正文(零批注通过后再定稿仍取原稿),不按会变的 `outcome`。

**手机交出是可恢复的出站事务**:先把批注标为已交出(带批次编号与时间)并落盘,再写原批次快照、上传;定稿请求先落"定稿在途"(批次编号、身份),再写快照。启动时,已交出但没有回执、也没有快照的批注按原批次编号重建快照再发;定稿在途同理。写盘失败就不发,界面说明没交出去。

**回执先到、新一轮快照后到**:next-round 批次交出后,在 Mac 的新一轮快照到达之前,这篇不再接受"为下一轮写的"新批注(底栏显示"已交出 · 等 Mac 开第 N+1 轮");被拒收则解除。快照先到、回执后到同样按批注身份收拢,不出重复提交。

**手机应用回执是可恢复的**

- 回执到达先落盘(写不进去就不推进拉取进度,下次再拉),再改批注状态(收下的记 `acceptedReviewId`,拒收的记原因),批注落盘成功后才标"回执已应用"。启动时把没标"已应用"的回执重新应用一遍(应用本身幂等)。重新发送读原批次快照与批注的创建身份,不读界面状态。
- 定稿请求没有批注可挂:手机按文档记"定稿请求在途"(批次编号),回执到了才清;界面据此显示"已请求定稿 · 等待 Mac"。

**复制到本轮(第 6.8 条落地)**

- 被拒收或旧版本上的批注,在本轮可批注时可以"复制到本轮":新 ID、本轮身份、`sourceNoteId` 指回原条;原记录不改。引文在本轮正文里找不到时,复制成总体意见并带上原引文。

## 7. 手机上的状态链

人话:每一步你都能看到批注走到哪了,"已上传"不会被说成"正在改稿","有程序在听"不会被说成"AI 已经在改"。

**传输状态**(每条批注 / 每个批次):

| 显示 | 含义 | 触发 |
|---|---|---|
| 本地已保存 | 批注在手机里了 | 每条批注落盘成功 |
| 等待同步 | 批次已打包,正在上传或等待网络 | 点「交给 AI」 |
| Mac 已接收 | 收到 Mac 的回执,批注已进旁注文件 | 回执到达 |
| 未被采用(原因) | 回执拒收 | 回执到达 |

**审阅生命周期**(每篇文档,与电脑端共用一套名字):批注中 / 已交出 / AI 正在修改 / 稿子回来了 / 已通过 / 已定稿 / 本轮已作废;冲突单独显示原因;恢复显示「已恢复到第 N 轮改稿前」,不显示成"稿子回来了";人工修改明确显示操作者,不归为 AI 修改。

**接手三档**(已交出时):没有 AI 接入 / ○○ 在线,等待领取 / AI 正在修改。`mdreview wait` 登记只表示有程序在听(30 秒续期、90 秒失效;因用户交出而返回时转为已交棒,15 分钟内仍算在线);只有 `claim` 或 `begin-apply` 成功才算领取。手机使用同样的事实与有效期,不把过期监听继续显示为在线。

状态只能由对应事件推进,界面不得凭猜测前进。默认假设 Mac 常开联网;联网但长时间没有回执时,显示"等待 Mac 在线",并提供"重新发送"。

新版到达时:手头没有未提交的批注,新正文**自动换进来**(字节通过指纹校验后);稿子回来时正文最上方是回稿卡(默认干净稿,「显示改动 / 隐藏改动」在本机对比手机留的上一版),其他情况顶部提示一句;手头还有未提交的批注(锚在旧正文上),保留"新版"按钮,由用户决定何时切换;旧批注标"上一轮的批注"。每条批注的处理结果(采纳 / 未采纳及原因)Mac 端记在版本事件里,随终态快照推到手机(第 5 节,v2.4);手机回稿卡显示采纳 / 未采纳条数与逐条结果。稿子回来后手机上可以接着批注(交出时开下一轮)或定稿(第 6.9 节)。

「交给 AI」是把东西发出去的动作,放在文档页底部常驻按钮上并显示未提交条数;无批注或稿子回来后的主动作是「通过 · 定稿」(手机阶段实现);「写总体意见」「查看改稿摘要」「重新发送」留在菜单里。

## 8. 三个独立的状态维度(Mac 端实现约束)

不用一组界面状态替换现有审阅状态机。三个维度各自存、各自显示:

1. **界面模式**:`read` | `edit`。只影响界面,不影响会话。
2. **审阅生命周期与当前写入者**:沿用现有状态机(`reviewing`、`ready_to_apply`、`applying` 及 `applyMode`、`complete` 及 `outcome`(approved / finalized / restored)、`conflict`、`cancelled`);底层状态名不随中文显示名改。附加事实:监听登记(`listeners.json`)、领取(`claimedAt / claimedBy`)、本轮成员(`memberAnnotationIds`)。"普通编辑登记":某文档处于普通编辑中时,智能体的 `mdreview open` 不得冻结它;登记在文档锁内进行,随编辑模式退出而解除,App 异常退出后由下次启动清理。
3. **同步状态**(按会话):`never` | `pushed` | `batch-pending` | `batch-received` | `receipt-sent`,以及最近一次推送与接收的时间、`revision`。

现有的写入状态检查、版本校验、幂等、备份、原子写入、外部变化检测全部保留。冻结审阅期间不能直接覆盖被批注版本;要改,只能另存副本(副本是新身份)。终态归档不可变:complete / cancelled 之后的普通编辑是工作稿,不改历史。

## 9. 真实数据保护

- **上传范围**:只上传进入审阅流程的文档及合同规定的事件;普通阅读、普通编辑不上传。
- **账号**:Mac 与 iPhone 必须登录同一个 Apple ID(iCloud);每个待上传项记录所属 iCloud 账号标识;账号切换后,旧账号的待上传队列不上传、不显示,等原账号登回来再续。(第 13 节:尚未实现)
- **本地备份**:动真实文件前先做整体快照(`mdreview snapshot`,服务启动也会每天自动做一份);快照含文档身份索引与版本目录;恢复可反悔。整体快照恢复后**重建当前身份**,不把身份与发布序号退回旧值;快照里的在途恢复事务隔离存放,不自动重放。
- **恢复**:在 Mac 执行,须无活动会话、无编辑登记、无未收敛写入;恢复事件保留恢复前当前稿、恢复后稿及来源版本,不修改旧轮批注结果、不继承旧领取信息;同步失败不回滚本地恢复。
- **删除**:在 Mac 上定稿或作废 30 天后,云端对应记录清理;手机本地副本随会话一起归档,可手动删除。(第 13 节:云端清理尚未实现)

## 10. 首版明确不做

- 一台 Mac 对多台手机、多台 Mac 对一台手机的组合;首版只验证一台 Mac 加一台 iPhone。
- 手机修改 Mac 会话的原文。
- 两端同时改同一条批注的合并。
- 手机独立文件自动回传 Mac(只能在 Mac 上显式转为新批注)。
- 指向其他 Markdown 的链接在手机上跳转。
- 镜像整个文件夹到手机(只推进入审阅流程的文档)。
- 非 UTF-8 文档同步正文。
- 恢复历史附件文件。

## 11. 验收场景

原有(旧协议已真机验证过 1~8):

1. 推送一份带图片和表格的真实方案到手机,图片完整显示。
2. 手机批注三条,强退 App,重开后三条都在。
3. 点「交给 AI」,断网,批注显示"等待同步";联网后自动上传,收到回执后显示"Mac 已接收",Mac 的旁注文件里正好三条。
4. 同一批次重复上传,Mac 的旁注文件仍是三条,返回的是原回执。
5. Mac 原文被外部改动后,手机再提交:按第 6 节顺序得到明确原因(已冲突则 `session-advanced`,否则 `version-mismatch`),不写入、有回执,批注保留在手机上。
6. 智能体改稿完成,手机收到新版(来自归档),显示"稿子回来了"和改稿摘要。
7. Mac 上 `mdreview open` 后 30 秒内手机收到通知并能打开;手机提交后 30 秒内 Mac 上等待中的 `mdreview wait` 返回。
8. Mac 合盖期间手机提交,手机显示"等待 Mac 在线";Mac 开盖联网后一分钟内收到批次并发回执。

v2.3 新增(对应设计 v4 第 12 节):

9. 同正文旧轮拒收:完成三轮 → 恢复到第二轮改稿前 → 再交出一轮 → 手机交回第二轮批次(正文完全相同、轮次不同)→ `round-advanced`,正文未改。
10. 逐条身份缺失(旧手机 App 或缺字段)→ `missing-identity`,提示更新;`--as-new-notes` 把旧文件批次转为本轮新批注并保留来源。
11. 原批次"重新发送"保持原身份;旧轮批注"复制到本轮"产生新 ID。
12. 仅状态更新不改挂旧缓存:手机缓存 UTF-8 稿 A → Mac 新轮为 GBK 稿 B 只推状态 → 手机显示 A 为旧轮只读,不能对 B 批注;正文字节不符本轮指纹时禁止批注。
13. 云端顺序:旧 revision 迟到不覆盖;同 revision 重试不重写;历史补发不回退当前。
14. 导入各阶段崩溃后重放(含空批次、全部去重的批次)都补齐到定稿回执,接受列表与首次一致。
15. 迟到批注不阻塞本轮完成;交出后新加的进下一轮。

v2.4 新增(第 5、6.9 节):

16. 稿子回来后手机批两条、交出:Mac 开第 N+1 轮、写入、交出,回执 `targetReviewId` 是新一轮;手机批注创建身份不变,`acceptedReviewId` 指向新一轮。
17. 同上,在开轮后、写批注前、交出后、回执前各杀一次进程:重启后补齐到同一个回执,只开一轮,不留孤立留底,Mac 上同时写的批注不被一起交出。
18. 两个 next-round 批次同时到:只开一轮,后到的 `round-advanced`;同一批次重复投递:回执不被拒收覆盖。
19. 手机定稿:回稿 / 通过 / 恢复 → 定稿;已定稿 → 原样接受不改时间;批注中且 Mac 上有未处理批注 → `has-open-notes`;Mac 上改过原文 → `version-mismatch`;先通过再定稿中途杀进程 → 重启补齐。
20. 新手机 + 旧 Mac:version 3 批次整批拒收,手机提示更新 Mac;旧手机 + 新 Mac:version 2 照旧。
21. 处理结果:随回稿推送,计数全量、列表受字节预算;正文没推时不推结果;升级后保留期内的回稿补推一次。
22. 持久化断点(逐个杀进程后重启):留底已写会话未写、会话已写批注未写、批注已写未交出、已交出回执未写、回执已写日志未清;定稿的通过后未定稿、定稿后回执未写;手机的批注已锁快照未写、快照已写未上传、回执已存批注未改。每个断点重启后都收敛到同一结果,不重复开轮、不重复交出。
23. "最新一轮"一致:第 N 轮完成后我自己改了一次(手工修改事件),手机针对这次手工修改开下一轮或定稿被接受,针对第 N 轮的被 `round-advanced`。

## 12. 同步通道:CloudKit 设计(2026-10-13 定,v2.3 补字段与发布先后)

人话:用苹果自家的 iCloud 当邮筒。Mac 把审阅中的文档投进你自己的 iCloud 私有空间,手机去取;手机把批注投进去,Mac 去取。只有登录同一个 Apple ID 的设备看得见,不经过任何第三方服务器。

| 容器 | `iCloud.app.draftback`,私有数据库,自定义区 `draftback`(支持按变更令牌增量拉取)。2026-10-14 随改名从 `iCloud.org.mdturn` 换过来,旧容器闲置。**新容器第一次用必须在 CloudKit 控制台(Safari)打开一次 Development 环境**,否则服务端一律回 500;打开后之前建的区会消失,辅助程序会自动重建 |
| Mac 接法 | 原生辅助程序 `Draftback Sync.app`(Swift + CloudKit 框架,无界面),随 Draftback.app 打包,由回稿启动与停止,主进程退出它随之退出;它通过本地服务的 `/api/app/sync/*` 接口取待推送项、报推送结果、导入批次。不用 CloudKit JS:网页登录令牌 30 分钟过期(勾"保持登录"也只有两周),常开同步会反复要求登录 |
| 签名 | 开发期用 Apple Development 证书 + Xcode 自动描述文件,且必须显式签 `icloud-container-environment = Development` 与 `icloud-container-development-container-identifiers`(自建工程 Xcode 不会代加,缺了 CloudKit 报 "Invalid bundle ID for container");发布用 Developer ID 证书 + 含 iCloud 容器的 Developer ID 描述文件,嵌在 `Contents/embedded.provisionprofile`,环境签 Production;发布前先把数据结构部署到容器的 Production 环境 |
| 记录类型 | `ReviewDocument`(记录名 = 文档标识):标题、会话标识、轮次、状态、事件类型与结果、恢复来源、版本指纹、正文是否可用、编码、正文(资产)、附件清单、改稿摘要、`revision`、监听 / 领取信息、处理结果(`results` JSON、采纳 / 未采纳条数,v2.4)、`macProtocol`(v2.4,Mac 支持的批次协议版本)、推送时间、推送者;`Attachment`(记录名 = 文档标识 + 相对路径校验码):所属文档、相对路径、字节数、校验码、文件(资产);`AnnotationBatch`(记录名 = 批次编号):**真实传递的 `version`**(带意图的是 3)、`intent`(v2.4,只在 version 3)、文档标识、会话标识、所依据版本、完成时间、设备、批注 JSON(逐条含创建身份);`Receipt`(记录名 = `receipt_` + 批次编号):接受 / 拒收、原因(含 `round-advanced`、`missing-identity`、`user-editing`、`has-open-notes`)、说明、批次原身份与指纹、执行的 `intent`、目标轮 `targetReviewId`(next-round 新开的一轮)、接受的批注 id、接收时间 |
| 谁写谁读 | Mac 写 `ReviewDocument`、`Attachment`、`Receipt`,只读 `AnnotationBatch`;手机写 `AnnotationBatch`,只读其余三种。"只有一方写"不能防止同一 Mac 的迟到发布覆盖新发布,所以还要下面的发布先后规则 |
| 发布先后 | 推送签名含发布格式版本(本版 `p3`,升级后保留期内每篇的最新一条各补推一次,带上 `macProtocol` 与处理结果)与正文、结果是否可用;可用性变了也分配新 `revision`。每次业务发布分配同一 `docId` 下跨轮单调递增的 `revision`,重试沿用原值。每次初读及条件写入(`ifServerRecordUnchanged`)冲突重读后,先比较业务 `revision`:云端较新则跳过;相同则确认同一次发布、不重写;本地较新才写入。手机拒绝较小 `revision`。补发历史不得回退 `latestVersionId` 或覆盖云端当前记录。整体恢复从 max(云端, 本地) + 1 续发 |
| 到达方式 | 手机:订阅该区的变更,收静默推送(不保证到达),外加打开 App 时拉取、前台每 20 秒拉一次保底;每次启动核对订阅是否还在;Mac:辅助程序每 15 秒拉一次区变更,区丢失自动重建 |
| 重装 / 多台 Mac | 辅助程序没有变更令牌时会重读云端全部历史:云端已有回执的批次一律跳过;这台 Mac 从没见过其文档标识的批次(别的电脑发起的审阅)不回执、不打扰手机 |
| 文档标识 | 由文档身份索引管理(第 3 节);不再按指纹沿用会话 |
| 同步状态 | 会话上记 `sync: { state, pushedHash, pushedAt, lastBatchAt, lastReceiptAt, error, revision }`,`state` 取第 8 节的五个值;`mdreview status` / `sync-status` 能看到 |
| 环境 | 开发期用容器的 Development 环境;TestFlight 与 Developer ID 包都走 Production |
| 清理 | 定稿或作废 30 天后,Mac 删除云端对应的四种记录(尚未实现) |
| 体积 | 正文与附件都走 CKAsset;单附件 20 MB、总量 100 MB 的打包上限不变 |

Mac 不在线时:手机照常批注、提交,批次留在云端;Mac 辅助程序上线后按第 6 节处理;手机在回执到达前显示"等待 Mac 在线"。
