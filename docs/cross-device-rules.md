# MDTurn 跨端规则(v2.1,2026-10-14)

> 路线图 v3 第 5 节的落地文档。它回答一个问题:同一份文档在 Mac 和 iPhone 之间来回时,**谁说了算、怎么认出是同一份、批注怎么走、出了岔子怎么办**。第一轮和第二轮的代码按这份规则写,验收也按它验。
> 不懂技术也能读:每条规则先说人话,再给实现要点。
>
> v2 改动(2026-10-13,开发者账户生效后与产品负责人确认的四个决定):只推审阅中的文档;`mdreview open` 即自动推、`complete` 即自动推新版;默认 Mac 常开;改完一轮手机收到新版正文加一段改稿摘要。第 12 节新增 CloudKit 同步通道的技术设计。

## 1. 几个词

| 词 | 意思 |
|---|---|
| 文档 | 一个 `.md` 文件。Mac 上它有路径;到了手机上,它只是一份内容。 |
| 版本指纹 | 文档内容算出的一串校验码(现有的 SHA-256)。内容改一个字,指纹就变。 |
| 审阅会话 | Mac 上"冻结一篇文档开始批注"这件事的记录,有自己的编号(现有的 review id)。 |
| 轮次 | 一个会话里"批注 → 改稿 → 再批注"的一圈。 |
| 批注批次 | 手机上点"完成本轮审阅"时打包的一组批注。 |
| 快照包 | 推到手机的那一份:正文、图片附件、版本指纹、会话信息。 |
| 回执 | Mac 收到批注批次后发回手机的确认:收了几条、拒了几条、为什么。 |

## 2. 两种流程,分开管

### 2.1 Mac 发起的审阅(主线)

人话:智能体在 Mac 上写好文档、用 MDTurn 发起审阅,手机上就自动出现这份文档;你批完点完成,批注回到 Mac,智能体接着改;改完新版又自动回到手机。

规则:

- **推送是自动的。** 智能体在 Mac 上 `mdreview open` 一份文档,这份文档就自动上云、推到手机,不需要再说"推到手机";`mdreview complete` 改完一轮,新版正文连同一段改稿摘要自动推到手机。普通打开(没有发起审阅)的文档一个字节都不上云。
- **原文归 Mac。** 原文件只在 Mac 上,手机永远不改原文,只提交批注。
- **轮次归 Mac。** 开新一轮、结束、定稿,都由 Mac 上的会话状态机决定;手机只能"提交本轮批注"。
- **手机针对指定版本提交。** 每个批注批次都带着它所依据的版本指纹;Mac 收到时核对,不一致就拒收并说明。

### 2.2 手机独立打开的文件(副线)

人话:你在手机"文件"里打开任意一份 Markdown,读、批、改、导出。

规则:

- 它和 Mac 的会话**无关**,即使文件名一模一样。
- 手机上独立打开的文件有自己的本地记录,不会自动与 Mac 的会话合并。
- 首版不提供"把手机独立文件的批注发回 Mac"。要走回 Mac,只能先在 Mac 上发起审阅。

## 3. 怎么认出是同一份

人话:不靠文件名,不靠 Mac 上的路径。文件改名、挪位置,会话不丢;复制一份、另存为,算新文档。

规则:

| 标识 | 是什么 | 谁发 | 存在哪 |
|---|---|---|---|
| 文档标识 | 一个随机编号,文档第一次进入 Mac 会话时分配 | Mac | Mac 的审阅索引(reviews.json);**不写进文档本身** |
| 会话标识 | 现有的 review id | Mac | 审阅索引 |
| 版本指纹 | 现有的 SHA-256 | Mac 算,手机核对 | 快照包、批注批次、回执里都带 |

- **改名、移动**:Mac 端打开新路径时,若内容指纹与某个活动会话一致,就沿用那个会话和文档标识(这是现有"按路径找会话"之外新增的"按指纹找会话")。
- **复制、另存为**:新路径、新文档标识、新会话;旧会话不受影响。
- **手机侧**:只认文档标识 + 会话标识 + 版本指纹,从不接触 Mac 路径;展示用的文件名只是显示文字。
- **外部改动**:审阅期间 Mac 上的原文被别的程序改了,现有的冲突拦截照旧生效;冲突状态同步到手机,手机显示"原文已变,等待 Mac 处理",不再允许提交。

## 4. 谁说了算(状态权威)

人话:三方各管一摊。Mac 管原文和会话;手机管自己还没交出去的批注;云端只是邮筒,不做裁判。

| 操作 | 谁发起 | 谁校验 | 谁最终落盘 |
|---|---|---|---|
| 推到手机 | Mac 上 `mdreview open` / `complete` 自动触发(也可手动 `mdreview push`) | Mac 会话状态机(只有活动会话能推) | Mac 写会话记录;云端存快照包 |
| 手机写批注 | 你在手机上 | 手机本地校验 | 手机本地(先落盘再说) |
| 完成本轮(提交批次) | 你在手机上 | 手机打包;Mac 收到后核对版本与会话状态 | Mac 写入 sidecar,再发回执 |
| 智能体改稿、完成本轮 | 智能体在 Mac 上 | 现有状态机 | Mac;新版快照包推到手机 |
| 定稿、取消 | 你在 Mac 上(或智能体 unlock) | 现有状态机 | Mac;状态同步到手机 |

- 桌面界面、CLI、同步模块遵守同一套状态转换规则,规则只有一份实现,三方都调用它。
- 云端数据永远可以从 Mac 重新生成;云端丢了不丢数据,Mac 的数据目录是唯一权威。
- 现有命令与旧数据全部向后兼容:老的 sidecar、老的审阅索引不做格式迁移就能用;新字段(文档标识、同步状态)缺省时按"从未同步过"处理。

## 5. 快照包里有什么

人话:推到手机的不只是文字,还有文档里引用的图片,不然手机上看到的是缺图的方案。

| 内容 | 规则 |
|---|---|
| 正文 | 原样的 Markdown 文本 |
| 版本指纹 | 正文的 SHA-256 |
| 本地图片与附件 | 文档里相对路径引用的、位于文档目录树内的文件,全部打包;单个文件超过 20 MB 或总量超过 100 MB 时,超出的文件不打包,清单里标"未打包",手机显示占位与提示 |
| 资源清单 | 每个资源的相对路径、字节数、校验码,保证手机看到的图是这一版对应的图 |
| 外链图片 | 不打包、不缓存;手机联网时直接加载,离线时显示占位 |
| 指向其他 Markdown 的链接 | 首版在手机上显示为普通文字链接,不可跳转 |
| 会话信息 | 文档标识、会话标识、轮次号、推送时间、推送者(Mac 设备名) |

同一会话再次推送(新一轮)时,只传指纹变化的文件;手机按清单核对,缺什么补什么。

## 6. 批注怎么走:批次、回执、去重

人话:手机上写的每一条先存在手机里,强退也不丢;点完成才打包上传;Mac 收到后回一张回执;重复上传不会重复算。

规则:

1. **先落盘**。每条批注写入手机本地存储后才算"已保存";界面显示"本地已保存"。
2. **打包**。点"完成本轮审阅"生成一个批次:批次编号(随机)、会话标识、所依据的版本指纹、批注列表、完成时间。批次生成后,这一轮的批注在手机上锁定,不能再改;要改,等下一轮。
3. **上传**。批次上传到云端(你自己 iCloud 账号的私有空间,只有登录同一 Apple ID 的设备看得见);失败自动重试;界面显示"等待同步"。
4. **Mac 接收**。Mac 收到批次后按顺序核对:
   - 会话还在审阅中吗?不在(已取消、已定稿、已进入改稿)→ 拒收,原因 `session-advanced`。
   - 版本指纹和 Mac 当前原文一致吗?不一致 → 拒收,原因 `version-mismatch`。
   - 批次编号见过吗?见过 → 直接返回上次的回执,不重复写入。
   - 都通过 → 整批写入 sidecar(逐条带批注 id,已存在的 id 跳过),会话进入"待改稿",通知等待中的智能体。
   - **批次没有完整收到时不写入、不改状态**:宁可让手机重传,不能让智能体拿着半份批注改稿。
5. **回执**。Mac 发回执:批次编号、接收时间、接受的批注 id、拒收原因。手机收到回执后把对应批注标为"Mac 已接收",或把拒收原因显示出来。
6. **迟到的旧批次**。Mac 已进入改稿或下一轮后才到的批次,按第 4 条拒收;手机上这些批注**保留**并标记"未被采用(原因)",由你决定在下一轮重新提交还是放弃。不静默丢弃。
7. **拒收后的批注**。永远留在手机本地,可以整批"转入下一轮"。

## 7. 手机上的状态链

人话:每一步你都能看到批注走到哪了,"已上传"不会被说成"正在改稿"。

| 显示 | 含义 | 触发 |
|---|---|---|
| 本地已保存 | 批注在手机里了 | 每条批注落盘 |
| 等待同步 | 批次已打包,正在上传或等待网络 | 点完成本轮 |
| Mac 已接收 | 收到 Mac 的回执,批注已进 sidecar | 回执到达 |
| 等待智能体 | 会话处于"待改稿" | Mac 状态同步 |
| 修改中 | 智能体正在改稿;文档页顶部横幅"Mac 正在修改,改完会自动换成新版" | Mac 状态同步 |
| 新版可复核 | 新一轮快照包已到,附一段改稿摘要(改了什么、哪些没采纳及原因) | 新快照包到达 |
| 原文已变,等待 Mac 处理 | 会话冲突 | Mac 状态同步 |

状态只能由对应事件推进,界面不得凭猜测前进。默认假设 Mac 常开联网;联网但长时间没有回执时,显示"等待 Mac 在线",并提供"重新发送"。
每条批注的处理结果(采纳 / 未采纳及原因)Mac 端已逐条记录在 sidecar 里;首版手机只显示改稿摘要,逐条展示放第二轮。

新版到达时(2026-10-14 定):文档页开着也不用退出——手头没有未提交的批注,新正文**自动换进来**,顶部提示"已更新到第 N 轮新版 · 点此看改稿摘要";手头还有未提交的批注(锚在旧正文上),保留"新版"按钮,由用户决定何时切换。Mac 端同理,改稿完成后自动加载新版。

"完成本轮"是每篇必走、唯一会把东西发出去的动作,放在文档页底部常驻按钮上并显示未提交条数,不藏进菜单;"写总体意见""查看改稿摘要""重新发送"这类可选动作留在菜单里。

## 8. 三个独立的状态维度(Mac 端实现约束)

不用一组界面状态替换现有审阅状态机。三个维度各自存、各自显示:

1. **界面模式**:`read` | `edit`。只影响界面,不影响会话。
2. **审阅生命周期与当前写入者**:沿用现有状态机(`reviewing`、`ready_to_apply`、`applying` 及 `applyMode`、`complete`、`finalized`、`conflict`、`cancelled`)。新增一个与会话并列的"普通编辑登记":某文档处于普通编辑中时,智能体的 `mdreview open` 不得冻结它,而是提示"用户正在编辑";登记随编辑模式退出而解除,App 异常退出后由下次启动清理。
3. **同步状态**(按会话):`never` | `pushed` | `batch-pending` | `batch-received` | `receipt-sent`,以及最近一次推送与接收的时间。

现有的写入状态检查、版本校验、幂等、备份、原子写入、外部变化检测全部保留。冻结审阅期间不能直接覆盖被批注版本;要改,只能另存副本。

## 9. 真实数据保护

- **上传范围**:只上传明确"推到手机"的会话。没推过的文档一个字节都不上云。
- **账号**:Mac 与 iPhone 必须登录同一个 Apple ID(iCloud);每个待上传项记录所属 iCloud 账号标识;账号切换后,旧账号的待上传队列不上传、不显示,等原账号登回来再续。
- **本地备份**:动真实文件前先做整体快照(`mdreview snapshot`,服务启动也会每天自动做一份);恢复可反悔。
- **删除**:在 Mac 上定稿或取消会话后,云端快照包与批次在 30 天后清理;手机本地副本随会话一起归档,可手动删除。

## 10. 首版明确不做

- 一台 Mac 对多台手机、多台 Mac 对一台手机的组合;首版只验证一台 Mac 加一台 iPhone。
- 手机修改 Mac 会话的原文。
- 两端同时改同一条批注的合并。
- 手机独立文件回传 Mac。
- 指向其他 Markdown 的链接在手机上跳转。
- 镜像整个文件夹到手机(只推审阅中的文档)。
- 手机上逐条查看每条批注的处理结果(首版只给改稿摘要)。

## 11. 第一轮验收要用到的场景

1. 推送一份带图片和表格的真实方案到手机,图片完整显示。
2. 手机批注三条,强退 App,重开后三条都在。
3. 点完成,断网,批注显示"等待同步";联网后自动上传,收到回执后显示"Mac 已接收",Mac 的 sidecar 里正好三条。
4. 同一批次重复上传,Mac 的 sidecar 仍是三条。
5. Mac 原文被外部改动后,手机再提交,收到 `version-mismatch` 拒收,批注保留在手机上。
6. 智能体改稿完成,手机收到新版,显示"新版可复核"和改稿摘要。
7. Mac 上 `mdreview open` 后 30 秒内手机收到通知并能打开;手机提交后 30 秒内 Mac 上等待中的 `mdreview wait` 返回。
8. Mac 合盖期间手机提交,手机显示"等待 Mac 在线";Mac 开盖联网后一分钟内收到批次并发回执。

## 12. 同步通道:CloudKit 设计(2026-10-13 定)

人话:用苹果自家的 iCloud 当邮筒。Mac 把审阅中的文档投进你自己的 iCloud 私有空间,手机去取;手机把批注投进去,Mac 去取。只有登录同一个 Apple ID 的设备看得见,不经过任何第三方服务器。

| 项 | 决定 |
|---|---|
| 容器 | `iCloud.org.mdturn`,私有数据库,自定义区 `mdturn`(支持按变更令牌增量拉取) |
| Mac 接法 | 原生辅助程序 `MDTurn Sync.app`(Swift + CloudKit 框架,无界面),随 MDTurn.app 打包,由 MDTurn 启动与停止,主进程退出它随之退出;它通过本地服务的 `/api/app/sync/*` 接口取待推送项、报推送结果、导入批次。不用 CloudKit JS:网页登录令牌 30 分钟过期(勾"保持登录"也只有两周),常开同步会反复要求登录 |
| 签名 | 开发期用 Apple Development 证书 + Xcode 自动描述文件,且必须显式签 `icloud-container-environment = Development` 与 `icloud-container-development-container-identifiers`(自建工程 Xcode 不会代加,缺了 CloudKit 报 "Invalid bundle ID for container");发布用 Developer ID 证书 + 含 iCloud 容器的 Developer ID 描述文件,嵌在 `Contents/embedded.provisionprofile`,环境签 Production;发布前先把数据结构部署到容器的 Production 环境 |
| 记录类型 | `ReviewDocument`(记录名 = 文档标识):标题、会话标识、轮次、状态、版本指纹、正文(资产)、附件清单、改稿摘要、推送时间、推送者;`Attachment`(记录名 = 文档标识 + 相对路径校验码):所属文档、相对路径、字节数、校验码、文件(资产);`AnnotationBatch`(记录名 = 批次编号):文档标识、会话标识、所依据版本、完成时间、设备、批注 JSON;`Receipt`(记录名 = `receipt_` + 批次编号,与 `AnnotationBatch` 同区不能重名):接受/拒收、原因、说明、接受的批注 id、接收时间 |
| 谁写谁读 | Mac 写 `ReviewDocument`、`Attachment`、`Receipt`,只读 `AnnotationBatch`;手机写 `AnnotationBatch`,只读其余三种。任何一种记录都只有一方写,不会两头改同一条 |
| 到达方式 | 手机:订阅该区的变更,收静默推送(不保证到达),外加打开 App 时拉取、前台每 20 秒拉一次保底;Mac:辅助程序每 15 秒拉一次区变更(Mac 常开,这个延迟可接受),后续再加推送 |
| 重装 / 多台 Mac | 辅助程序没有变更令牌时会重读云端全部历史:云端已有回执的批次一律跳过(否则会把"已采用"覆盖成"拒收");这台 Mac 从没见过其文档标识的批次(别的电脑发起的审阅)不回执、不打扰手机 |
| 文档标识 | 审阅索引新增 `docId`(随机);同一路径后续轮次沿用,按指纹找到的会话也沿用 |
| 同步状态 | 会话上记 `sync: { state, pushedHash, pushedAt, lastBatchAt, lastReceiptAt, error }`,`state` 取第 8 节的五个值;`mdreview status` 能看到 |
| 环境 | 开发期用容器的 Development 环境;TestFlight 与 Developer ID 包都走 Production |
| 清理 | 定稿或取消 30 天后,Mac 删除云端对应的四种记录 |
| 体积 | 正文与附件都走 CKAsset;单附件 20 MB、总量 100 MB 的打包上限不变 |

Mac 不在线时:手机照常批注、提交,批次留在云端;Mac 辅助程序上线后按第 6 节处理;手机在回执到达前显示"等待 Mac 在线"。

2026-10-14 真机验证通过(两轮):Mac 推 → 手机"来自 Mac"出现(含 png/svg 附件)→ 手机批注交回 → Mac 收到并回执 → 改稿中横幅 → 改完手机正文自动换新 + 改稿摘要。
